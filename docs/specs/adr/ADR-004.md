# ADR-004 — Keep the audit, history and job-delegation objects in one NoName database, one schema per area, installed by a versioned idempotent script

## Context and problem statement

ARCH-001#DEC-04 asks whether the audit objects, the job-delegation objects and the history database share one database on the instance, and how NoName installs and upgrades it. PRD-001 v2 raises it as a NEEDS ADR marker affecting FR-026, FR-027, FR-032, FR-033, FR-036 and FR-037. The requirements that write audit rows (FR-010, FR-014, FR-016, FR-022, FR-023) or read history (FR-025, FR-047, FR-050, FR-053) depend on the same answer. All of them are in the backlog. The database's name waits on the product name (Q-NN-001).

## Decision drivers

- PRD-001#NFR-007: every generated script opens in a new window, unexecuted.
- PRD-001#FR-027: signed wrapper procedures need server-scope objects as well as database objects.
- PRD-001#FR-032: the audit record is written in the same transaction as the action by default.
- A DBA reviews and grants one install, not three.

## Considered options

1. One NoName database, one schema per area, with a versioned, re-runnable install and upgrade script.
2. A separate database per area, each with its own installer.

## Decision outcome

**Chosen option:** option 1. Bryan Ankielewicz decided this on 2026-11-06. The decision text he pasted and confirmed says one database undersells what FR-027 needs:

> List the server-scope objects the install touches: the certificate's login in master for signed wrapper procedures, server-level grants, and the Agent jobs. One schema per area (audit, history, jobs) so grants map to one role per area. A schema_version table, numbered idempotent steps, each step transactional where SQL Server allows it, and a drop script shipped alongside. The script is generated from resources in Core so it is unit-tested, and opens unexecuted (NFR-007).

On installing into a database the organization already has, he answered: "This can be an option - yes but not mandatory." So the installer may also offer to install the same schemas into an existing DBA database, and a new NoName database stays the default.

### Consequences

- Good: grants map to one role per schema, so a DBA can grant audit, history and job delegation separately.
- Good: one schema_version table and one numbered step list give one upgrade path, and the drop script removes everything the install added.
- Good: the install script is generated and unit-tested in Core, and the user runs it.
- Bad: server-scope objects (the certificate's login in master, server-level grants, Agent jobs) sit outside the database, so the drop script must remove them explicitly. Steps that SQL Server can't run in a transaction need their own idempotency checks.
- Bad: installing into an existing DBA database must avoid name clashes with schemas that database already has. The first epic that ships the installer specifies that check.

### Confirmation

- The first epic that ships FR-032 (with FR-014) specifies the audit schema, the schema_version table, the numbered steps and the drop script, and unit-tests the generated script in Core under the 95% gate.
- A test instance shows install, a re-run with no change, an upgrade from the previous version, and the drop script leaving no NoName object behind, server-scope objects included.

## Pros and cons of the options

### One database, one schema per area, versioned script
- Good, because there is one install to review and one upgrade path.
- Good, because the schemas keep each area's grants separate.
- Bad, because one database holds data with different retention needs (audit against history).

### A separate database per area
- Good, because each area is fully independent.
- Bad, because a DBA reviews three installs and three upgrade paths, and enterprise shops that refuse one new database refuse three.
