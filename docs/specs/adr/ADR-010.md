# ADR-010 — Disclose the replica the extension's own connection observes, and verify the window's replica only by finding its session

## Context and problem statement

ARCH-001#DEC-03 asks how the extension's own connection is shown to reach the same server and replica as the query window when the window connects through an availability-group listener, an alias or read-only intent. ADR-003 answered it with a SPID lookup and a fallback that compared SERVERPROPERTY('ServerName') and the replica role with the window's. Moving that answer into PRD-001 showed two flaws in the fallback, and this ADR supersedes ADR-003.

The extension opens its own connection with the window's settings, application intent included (PRB-SQL-03). Its role therefore agrees with that intent whenever routing works. A check of role against intent compares the extension with itself: it can raise false alarms (no read-only routing configured, or a window connected directly to a secondary) but can never see the window on another replica, because nothing in it observes the window. Predicting the window's replica from the routing list doesn't work either. Routing happens only when the login names a database in the availability group, and PRB-SQL-01 reads the window's current database, not the one it logged in with. Comparing names fails on aliases, fully qualified names, IP addresses and ports, and through a listener the window's connection info carries the listener's name, not the replica's.

## Decision drivers

- What the user sees must describe the replica that was actually read, never a guess.
- PRD-001's launch must be provable on the local standalone instance, without an availability group.
- PRD-001#NFR-015: a stated state, never an error dialog; PRD-001#NFR-045: a disabled feature names its probe.
- Read-only routing is round-robin since SQL Server 2016, so two connections with the same settings can land on different secondaries.

## Considered options

1. Disclose what the own connection observes as a launch must, and verify the window's replica only by finding its session (the SPID path) as a should.
2. Check the own connection's role against the window's application intent (the first form of Bryan's decision of 2026-11-06).
3. Predict the window's replica from the read-only routing list and compare server names (the session's refinement of option 2).
4. ADR-003's SPID lookup with its name-and-role fallback.

## Decision outcome

**Chosen option:** option 1, verification by observation, never prediction, in three tiers. Bryan Ankielewicz decided this on 2026-11-06, in the decision text he pasted and confirmed (it corrects his own earlier answer):

> Drop role-versus-intent entirely; it compares the extension against itself and detects nothing about the window. Verify by observation, never prediction, in three tiers.
>
> Must at launch (NFR-049): the extension copies the window's settings as PRB-SQL-03 proves, and every read discloses the replica it actually landed on: SERVERPROPERTY('ServerName'), its role from the HADR DMVs or 'not in an availability group', and whether it was routed (the connected-to name differs from the server name). That shows on the connection chip and in every prompt's context header. Provable on the local standalone instance, so launch does not wait on an availability group.
>
> Should (the SPID path): when the window's SPID is readable, look it up in sys.dm_exec_sessions on the own connection. Found means verified. Not found means enumerate sys.availability_replicas, find the SPID on one of them, and reconnect the own connection directly to that replica by its server name with no intent, which removes routing from the problem, round-robin included. Re-verify after each window reconnect, since a failover moves the window and leaves a pinned own connection behind. 'Different replica, reading nothing' is shown only when the SPID is proven elsewhere and that replica cannot be reached.
>
> Advisory, never a state: ReadOnly intent landing on the primary shows 'no read-only routing in effect' as information. Both edge cases become correct disclosures instead of misfires.

Approving the round-11 plan in plan mode, Bryan also approved this ADR's supersession of ADR-003. In a prompt's context header the server name is redacted like any other identity (PRD-001#FR-006); only the role travels as a value.

**Changed before this ADR was first committed** (Bryan Ankielewicz, 2026-11-06, after a review note): three changes to the quoted text above.

- **The routed flag is dropped from the must.** "The connected-to name differs from the server name" is a name comparison, which fails on fully qualified names, IP addresses, ports and aliases, and no client property or DMV reports routing per session.
- **The advisory line is purely observational:** "ReadOnly intent, reading the primary." "No read-only routing in effect" claimed something about the routing configuration, and misfires on a window connected directly to the primary by name with ReadOnly intent, which is normal.
- **The role disclosure degrades under a missing permission.** Reading the role from the HADR DMVs needs VIEW SERVER STATE, so a login without it shows "role not readable", never a failed read or a false "not in an availability group" (INPUT-NN-021, PRD-001#NFR-009). The must is then provable on the permission-missing path too.

Matching the window's host against the listener tables is parked, with no scope now: it is still a name match, it misses aliases and CNAMEs, and the SPID path owns "which replica".

### Consequences

- Good: the launch must is provable on a standalone instance, where PRB-SQL-03 logs the server name and the role, "not in an availability group", and on the permission-missing path, where the role shows "role not readable".
- Good: no false alarms. A ReadOnly window on a primary and a window connected directly to a secondary are disclosed correctly.
- Good: the SPID path removes routing from the problem by reconnecting directly to the replica that holds the window's session.
- Bad: until the SPID path passes (PRB-SQL-01's window-SPID read, RES-NN-001 0.2.4), the extension discloses where it is but can't prove the window is there too.
- Bad: the SPID path's enumerate-and-reconnect branch is tested only where an instance in an availability group exists (PRD-001 FR-059's condition).

### Confirmation

- PRB-SQL-03 (RES-NN-001 0.2.4) logs SERVERPROPERTY('ServerName') and the role, "not in an availability group", or "role not readable" for a login without VIEW SERVER STATE. It passes on the local instance when both are read and logged.
- PRB-SQL-01 (RES-NN-001 0.2.4) reads the window's SPID, and PRB-SQL-03 logs whether that SPID was found on the own connection.
- The first epic that opens the own connection specifies the disclosure on the connection chip and in the prompt header, and unit-tests the tier logic in Core.

## Pros and cons of the options

### Disclose by observation, verify by the window's session
- Good, because everything shown was observed.
- Good, because the must doesn't wait on an availability group.
- Bad, because mismatch detection is a should and needs the window's SPID.

### Role against intent
- Good, because it is one query.
- Bad, because it compares the extension with itself, detects nothing about the window, and misfires on two common setups.

### Predict from routing and compare names
- Good, because it would need no SPID.
- Bad, because the window's login database isn't known, so routing can't be predicted, and names differ through aliases, FQDNs, IPs and ports.

### ADR-003's SPID lookup with the name-and-role fallback
- Good, because its SPID lookup is right.
- Bad, because its fallback is option 2's flaw plus name comparison.
