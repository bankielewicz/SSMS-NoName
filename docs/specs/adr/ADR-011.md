# ADR-011 — Disclose the replica the own connection observes, and verify the window's replica only when exactly one replica holds its session

## Context and problem statement

ARCH-001#DEC-03 and DEC-10 ask how the extension's own connection is shown to reach the same server and replica as the query window, through an availability-group listener, an alias or read-only intent. ADR-010 answered with three tiers, but two independent Codex reviews of 2026-11-06 found that its verification rule, "look the window's SPID up in sys.dm_exec_sessions; found means verified", can falsely verify. A SPID is server-local: another replica can hold an unrelated session with the same number, login and program name, so a routed own connection would pass the check and the instance window and FR-006's identity lookups would silently read the wrong server. Earlier the same day, the routed flag and the "no read-only routing in effect" line were dropped from ADR-010's text before it was committed. This ADR supersedes ADR-010 and states the mechanism exactly as PRD-001 version 3 does in FR-061 and NFR-049.

## Decision drivers

- Nothing shown as verified may rest on a match that can collide.
- PRD-001's launch must (NFR-049) is provable on the local standalone instance, without an availability group.
- PRD-001#NFR-009 and NFR-015: a missing permission disables only what needs it and shows a stated state.
- No DMV carries the client connection's identifier: sys.dm_exec_connections has only its own server-side connection_id, so no deterministic identifier exists.

## Considered options

1. Disclose what the own connection observes (must), and verify the window's replica only when exactly one replica in the group holds a session matching its session_id, login_name, host_name and host_process_id (should).
2. ADR-010's rule: a bare SPID match, found means verified.
3. A check of the own connection's role against the window's application intent.
4. Predicting the window's replica from the read-only routing list and comparing names.

## Decision outcome

**Chosen option:** option 1. Bryan Ankielewicz decided this on 2026-11-06, answering the Codex reviews, and approved this supersession of ADR-010 in the same session. The mechanism, as PRD-001 version 3 states it:

- **Must, NFR-049.** Every read on the extension's own connection, which copies the window's settings as PRB-SQL-03 proves, discloses the replica it landed on: SERVERPROPERTY('ServerName') and its role from the availability-group DMVs, or "not in an availability group", or "role not readable" for a login without VIEW SERVER STATE (NFR-009), never a failed read. Where FR-061 runs, it also shows verified or unverified. This appears on the window's connection chip and in every prompt's context header, where the server name is redacted like any other identity (FR-006) and only the role travels as a value. ReadOnly intent on a primary shows "ReadOnly intent, reading the primary" as information, never a state.
- **Should, FR-061.** With the window's SPID (PRB-SQL-01), the extension searches every replica that sys.dm_hadr_availability_replica_cluster_states lists (outside an availability group, the instance itself), never stopping at the first match, for a session whose session_id, login_name, host_name and host_process_id (the SSMS process) match the window's, leaving out the extension's own sessions. Exactly one matching replica means verified once the own connection is on it: if it isn't the current one, the own connection reconnects to its replica_server_name with the window's own settings, application intent included, and the destination check must pass on both conditions, the window's session is found on the new connection and SERVERPROPERTY('ServerName') equals that replica_server_name, compared case-insensitively. No match, more than one, replicas the view can't list, any replica unreachable, a connection that fails (a replica name that doesn't resolve from the client, a named instance with no SQL Browser or known port, a ReadOnly secondary refusing the intent, or ALLOW_CONNECTIONS = NO), a failed destination check, or a login without VIEW SERVER STATE (VIEW SERVER PERFORMANCE STATE on SQL Server 2022 and later) means unverified, with the reason shown and NFR-049's disclosure still shown, never an error state. The pin to a replica is dropped and the search redone whenever the window's connection changes, so a failover never leaves the extension reading a demoted replica. On one instance the session tuple identifies one session; the only collision left is this same SSMS process holding a same-numbered session on another replica of the group.

Extended Events aren't used to find the window's connection.

**Corrected before its pull request merged** (Bryan Ankielewicz, 2026-11-06, after a Codex review of 7d9ed66). The rule, stated once: an ADR may be corrected in place until the pull request that introduces it merges; after merge, it is superseded. Nothing had merged and no epic cited this ADR. The corrections, made in the text above:

- The search lists replicas from sys.dm_hadr_availability_replica_cluster_states, which needs VIEW SERVER STATE (VIEW SERVER PERFORMANCE STATE on SQL Server 2022 and later), instead of sys.availability_replicas, which needs VIEW ANY DEFINITION, outside PRD-001#NFR-009's ceiling. Replicas the view can't list make the result unverified.
- The reconnect keeps the window's application intent instead of none, because no intent defaults to ReadWrite, which a ReadOnly secondary refuses and read/write redirection sends to the primary. The destination check must then pass on both conditions; the two names compared are both server metadata, not the rejected comparison of client-typed names.
- Any connection failure is unverified with its reason, never an error state.
- The pin to a replica is dropped and the search redone whenever the window's connection changes.

### Consequences

- Good: no outcome is shown as verified unless exactly one replica holds a matching session, so a collision becomes unverified, not false success.
- Good: the launch must doesn't wait on an availability group, and it holds on the permission-missing path.
- Bad: two SSMS sessions of the same process with the same number on two replicas leave the window unverified even when the extension is on the right replica.
- Bad: the search needs a connection to every replica, and an unreachable one makes the result unverified.

### Confirmation

- The decision rule (one, many, none, unreachable) is a Core unit test over synthetic candidates under the 95% gate. It is the evidence for the collision case, which can't be forced on a live group.
- PRB-SQL-03 (RES-NN-001 0.2.4) logs the server name and role, "not in an availability group" locally or "role not readable" without the permission, for NFR-049. Its forced not-found step runs the search, the reconnect and the destination check on an instance in an availability group with two replicas or more, for FR-061, and logs whether the cluster-states view lists the local group's replicas.
- PRB-SQL-01 reads the window's SPID, reported as a result of its own that gates only FR-061.

## Pros and cons of the options

### Disclose, then verify by exactly one matching session
- Good, because a collision can't produce a false "verified".
- Bad, because verification needs every replica reachable and the permission to see sessions.

### ADR-010's bare SPID match
- Good, because it is one lookup.
- Bad, because a bare SPID match is server-local and can collide across replicas: an unrelated session with the same number, login and program name on another replica passes it.

### Role against intent
- Bad, because it compares the extension with itself and observes nothing about the window.

### Predict from routing and compare names
- Bad, because the window's login database isn't known, so routing can't be predicted, and names differ through aliases, fully qualified names, IP addresses and ports.
