# ADR-009 — Build Core from one shared source project into two assemblies with different identities, one per VSIX

## Context and problem statement

ARCH-001#DEC-09 asks how the Core library, which both the Diagnostics VSIX and the product VSIX ship, avoids the first-loaded-wins clash inside one SSMS process. ADR-008 records the trap: two extensions that ship an assembly with the same name at different versions both run whichever copy loads first. ADR-008 settles the host layer (source-shared, or a per-VSIX assembly name) and leaves Core's fix to the first packaging epic. If Core clashed, a user who updated only one VSIX would have both running the same Core, and the canary (FR-004) could be testing the product's code instead of its own.

Today the Diagnostics VSIX takes Core through a ProjectReference to an assembly named `NoName.Diagnostics.Core` (observed practice, ARCH-001#EVD-07).

## Decision drivers

- PRD-001#FR-004: the canary must test its own code after an SSMS update.
- PRD-001#NFR-014 and NFR-045: a break disables only its feature, and says why.
- PRD-001#NFR-044: the logic stays under the 95% gate, with no code left untested.
- PRD-001#NFR-016: the session log records what loaded.

## Considered options

1. One shared source project built into two assemblies with different identities, one per VSIX.
2. Strong naming with exact versions.
3. Merging Core into each package assembly with ILRepack.
4. A version check at load, alone.

## Decision outcome

**Chosen option:** option 1. Bryan Ankielewicz decided this on 2026-11-06, in the decision text he pasted and confirmed:

> Core is built from one shared source project (.projitems) imported by two thin SDK csprojs: NoName.Diagnostics.Core, shipped only in the Diagnostics VSIX, and a second assembly under the product's own name (placeholder NoName.Core until Q-NN-001 settles it), shipped only in the product VSIX. Namespaces stay identical; only the assembly identity differs. Neither VSIX exchanges objects with the other, so two copies in one SSMS process are harmless, and neither VSIX declares a dependency on the other. The test project references one of the two, so no untested code appears and the coverage gate is untouched; the ADR says so explicitly. On package load, each VSIX writes into its session/start line the full name, location and informational version (git SHA) of its own Core and of every other NoName.* assembly already in the process.

As the decision text asks, this ADR states it explicitly: **the coverage gate is untouched.** Both assemblies compile the same source files, the test project references one of them, and no exclusion, skip or lowered minimum is added. The second assembly adds no source that the tests don't cover.

### Consequences

- Good: each VSIX always runs its own Core, so updating one never changes the code the other runs, and the canary tests what it shipped with.
- Good: the session/start line shows which Core and which other NoName.* assemblies were in the process, so a mismatch is visible in the log a user attaches (NFR-034).
- Good: no key management and no IL rewriting in an MIT repository.
- Bad: two copies of Core load in one SSMS process when both VSIXs are installed, costing memory twice. This is harmless only while neither VSIX passes Core objects to the other; that rule must hold in every later epic.
- Bad: the product assembly's name is a placeholder (NoName.Core) until Q-NN-001 settles the product name, so a rename follows.

### Confirmation

Both VSIXs are installed together in SSMS 22. Each session log shows its own Core loaded from its own extension folder, and the ActivityLog is free of binding errors. The first packaging epic's spec carries this check, and review confirms that the test project and coverage settings are unchanged apart from pointing at the shared source.

## Pros and cons of the options

### One shared source, two assembly identities
- Good, because it prevents the clash instead of detecting it.
- Good, because the source and tests stay single.
- Bad, because two copies load when both VSIXs are installed.

### Strong naming with exact versions
- Good, because the loader tells the versions apart in principle.
- Bad, because auto-generated binding redirects and shell probing can unify them anyway, and it adds key management to an MIT repository.

### Merging Core into each package assembly with ILRepack
- Good, because each VSIX ends up with one assembly.
- Bad, because it breaks symbols and debugging, for no gain over renaming.

### A version check at load, alone
- Good, because it is simple.
- Bad, because it detects the clash but doesn't prevent it.
