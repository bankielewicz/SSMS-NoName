# ADR-008 — Ship NoName Diagnostics and the product as two VSIXs from one solution, with the host layer source-shared and the probe catalog in Core

## Context and problem statement

ARCH-001#DEC-08 asks whether NoName Diagnostics and the product ship as one VSIX or two. FR-004 keeps Diagnostics as an SSMS-update canary, and FR-008 gives it a tool window. The product is 0.1.0, installed per user into SSMS 22 with SSMS's own VSIXInstaller (PRD-001 section 11). Both need the same late-bound access to SSMS's internal APIs, and NFR-045 asks every disabled feature to name the probe that proves it.

## Decision drivers

- PRD-001#FR-004: the canary must keep working when product code breaks.
- PRD-001#NFR-014 and NFR-045: a broken SSMS API disables only its feature, which names its probe.
- PRD-001#NFR-044: every SSMS type is bound late.
- PRD-001#NFR-001 and NFR-038: SSMS 22, Windows x64, per-user install.

## Considered options

1. Two VSIXs, Diagnostics and the product, sharing the late-bound host layer.
2. One VSIX that carries both.

## Decision outcome

**Chosen option:** option 1, two VSIXs. Bryan Ankielewicz decided this on 2026-11-06. The decision text he pasted and confirmed names one trap and one mechanism:

> Two VSIXs that ship the same shared assembly name at different versions collide inside one SSMS process; the first loaded wins. The shared late-bound host layer is therefore source-shared (a shared project) or compiled under a per-VSIX assembly name. The probe catalog lives in Core, so the product VSIX runs it as a self-check after an SSMS update; that is the mechanism behind NFR-044's "disables a feature rather than the extension". Both VSIXs build from one solution with one version number.

### Consequences

- Good: the canary installs and runs on its own, so a broken product build can't hide an SSMS break.
- Good: the product runs the same probe catalog as a self-check, so a feature disabled after an SSMS update names the probe that failed (NFR-045).
- Bad: the collision trap applies to every assembly both VSIXs ship, Core included, not only the host layer. One solution and one version number keep released pairs in step, but a user who installs mismatched versions of the two still gets whichever Core loads first. The first epic that packages the product names how Core is shipped: one version, a per-VSIX assembly name, or a check at load.
- Bad: two manifests and two installs to maintain.

### Confirmation

- The first epic that packages the product shows both VSIXs installed together in SSMS 22, each loading its own host layer, with the ActivityLog free of assembly-binding errors.
- After an SSMS update, the product's self-check and the Diagnostics run report the same probe results.

## Pros and cons of the options

### Two VSIXs
- Good, because the canary stays independent of product code.
- Bad, because shared assemblies must be source-shared or renamed per VSIX to avoid the first-loaded-wins collision.

### One VSIX
- Good, because there is one package, one install and no collision.
- Bad, because a product fault that stops the package from loading also stops the canary, and the diagnostic tools ship to every product user.
