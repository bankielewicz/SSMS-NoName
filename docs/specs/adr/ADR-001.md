# ADR-001 — Run redaction in-process in a pure Core library with no SSMS reference

## Context and problem statement

ARCH-001#DEC-01 asks where redaction runs: inside the SSMS process, or in a separate engine with no SSMS dependency that the VSIX calls. It also asks whether NFR-044's rule stands, that the logic lives in a library with no SSMS reference. PRD-001 v2 raises it as a NEEDS ADR marker affecting FR-001, FR-002, FR-005, FR-006, FR-007, FR-009 and FR-051.

NFR-003 requires T-SQL parsing inside SSMS to use SSMS's bundled ScriptDom (18.0.115 today). NFR-018 keeps SQL, parsing and file reads off SSMS's UI thread. NFR-044 puts the logic under the repository's 95% line-coverage gate. IDEA-NN-001's architecture sketch proposed "a .NET library and command-line tool with no SSMS dependency". The existing `src/NoName.Diagnostics.Core` is a netstandard2.0 library with no SSMS reference, loaded in-process by the VSIX.

## Decision drivers

- PRD-001#NFR-003: SSMS's own ScriptDom inside SSMS.
- PRD-001#NFR-044: logic in a library with no SSMS reference, at the 95% gate.
- PRD-001#NFR-018: nothing heavy on the UI thread.
- PRD-001#FR-007: literals and comments are found by parsing T-SQL, and plan and deadlock values by reading the XML.
- Later wrappers (BRN-001 IDEA-10's CLI, IDEA-06's MCP channel) should reuse the same engine.

## Considered options

1. An in-process library with no SSMS reference, with ScriptDom bound by name at runtime.
2. A separate local engine process that the VSIX calls.

## Decision outcome

**Chosen option:** option 1, an in-process library with no SSMS reference. NFR-044 stands. Bryan Ankielewicz chose it on 2026-11-06, with these constraints for this ADR from the decision text he pasted and confirmed:

> Keep the redaction engine pure: a string and a context in, a string and a mapping out, no SSMS, no I/O. ScriptDom is bound by name in the VSIX host layer; the Core library exposes a parser interface so CI tests run against the NuGet ScriptDom while SSMS supplies 18.0.115 at runtime. Crash isolation comes from catching everything at each command boundary and never running on the UI thread (NFR-018), not from a second process. The pure shape keeps IDEA-10's CLI and IDEA-06's MCP wrappers trivial later.

On the viewer question (ARCH-001#DEC-02, ADR-002), the same text adds: "Core parses ShowPlan XML and deadlock XML into a graph model from day one, because FR-042 already needs operators, warnings and estimated-against-actual rows from that XML." So the redaction engine's element-by-element reading of plan and deadlock XML (FR-007) and the graph model share one Core parser for each XML kind.

### Consequences

- Good: the redaction engine has no I/O and no host types, so every rule is unit-tested in CI on Linux and Windows under the 95% gate.
- Good: NFR-003 holds. Inside SSMS the parser interface is backed by SSMS's bundled ScriptDom 18.0.115, bound by name in the host layer.
- Good: a later CLI or MCP wrapper is a thin host over the same engine.
- Bad: CI parses with the NuGet ScriptDom, which may differ from 18.0.115. A rule that depends on the parser version needs a check in SSMS (PRB-PARSE-01) as well as its unit test.
- Bad: a fault in the engine runs in SSMS's process. The only guard is the catch-all at each command boundary, together with NFR-014.

### Confirmation

- The Core project keeps no SSMS or ScriptDom compile-time reference (checked in review of every pull request that touches its project file).
- The redaction engine's public entry point takes a string and a context and returns a string and a mapping, with no file, network or clipboard access; its tests run under the 95% gate.
- PRB-PARSE-01 passes in NoName Diagnostics with the parser interface backed by SSMS's ScriptDom.
- The first epic that ships FR-001 shows each command's catch-all boundary in its spec.

## Pros and cons of the options

### An in-process library with no SSMS reference
- Good, because it uses SSMS's own ScriptDom, as NFR-003 requires.
- Good, because it is one process, with nothing extra to start or keep light.
- Good, because it matches the shape `src/NoName.Diagnostics.Core` already has (observed practice).
- Bad, because a fault in the engine runs inside SSMS, guarded only by the command boundary.

### A separate local engine process
- Good, because a crash in the engine can't take SSMS down.
- Bad, because it can't use SSMS's bundled ScriptDom, so NFR-003 would have to change.
- Bad, because it adds a process to start, keep light and secure, with inter-process calls for every prompt.
