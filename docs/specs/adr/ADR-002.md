# ADR-002 — Show plans and deadlock graphs through one Core viewer interface: SSMS's own viewers in the MVP, native WPF viewers as the first post-MVP epic

## Context and problem statement

ARCH-001#DEC-02 asks how execution plans and deadlock graphs are shown. In the MVP the choice is SSMS's own viewers or an out-of-process viewer. After the MVP, native viewers inside the extension must keep within NFR-018 and NFR-019. Any viewer the decision names keeps within NFR-048. PRD-001 v2 raises it as a NEEDS ADR marker affecting FR-039, FR-042, FR-043, FR-056, FR-057 and FR-058.

Under PRD-001 section 11, an out-of-process viewer counts at launch only once the viewer decision names it and its hand-off has passed a probe in NoName Diagnostics. Until then only SSMS's own viewer counts.

## Decision drivers

- PRD-001#NFR-048: plan and deadlock XML stays on this machine, in a temp file deleted when the viewer closes or SSMS exits.
- PRD-001#FR-042: the plan inspector needs operators, warnings and estimated-against-actual rows from the plan XML whatever viewer shows the graph.
- PRD-001#FR-056 and FR-057: native viewers come after the MVP.
- PRD-001#NFR-018 and NFR-019: no heavy work on the UI thread, and no lag.
- Section 11's should rule: FR-039, FR-042 and FR-058 move to later unless their hand-off has passed a probe.

## Considered options

1. SSMS's own viewers in the MVP, then native viewers in the extension.
2. An out-of-process viewer in the MVP.

## Decision outcome

**Chosen option:** option 1, with every viewer behind one interface in Core. Out-of-process viewers are not chosen. Bryan Ankielewicz decided this on 2026-11-06, in the decision text he pasted and confirmed:

> The native viewer is the target architecture, not an afterthought. Core parses ShowPlan XML and deadlock XML into a graph model from day one, because FR-042 already needs operators, warnings and estimated-against-actual rows from that XML. Every viewer sits behind one interface in Core; the MVP's implementation writes the XML to a temp file and opens it in SSMS's own viewer under NFR-048; the native WPF renderer (FR-056, FR-057) is the first post-MVP epic and replaces that implementation without touching callers. The deadlock graph is the first native viewer because it is the smaller renderer. Out-of-process viewers are not chosen.

Because no out-of-process viewer is named, this ADR proposes no new hand-off probe for RES-NN-001. The MVP's hand-off is tested by PRB-LIVE-06 (plans) and PRB-XE-06 (deadlock graphs), as PRD-001 section 11 already says.

### Consequences

- Good: FR-042's warnings and row comparisons work from the Core graph model, whichever viewer draws the graph.
- Good: callers such as the Query Store tab, the deadlock list and row-to-prompt depend only on the interface, so the native renderer replaces the MVP implementation without touching them.
- Good: NFR-048 applies to exactly one implementation, the temp-file hand-off.
- Bad: with no out-of-process fallback, FR-039, FR-042 and FR-058 move to later at launch if PRB-LIVE-06 or PRB-XE-06 fails.
- Bad: the native renderers (DrawingVisual, ADR-006) are real work after the MVP and must be measured against NFR-019.

### Confirmation

- The first epic that ships FR-042 or FR-058 specifies the viewer interface and the Core graph models, and unit-tests the plan and deadlock parsers under the 95% gate.
- The MVP's temp-file implementation is checked against NFR-048: the file is under the user's temp folder and is deleted when the viewer closes or SSMS exits.
- The native deadlock viewer (FR-057) is the first post-MVP epic and changes no caller of the interface.

## Pros and cons of the options

### SSMS's own viewers, then native viewers
- Good, because the MVP viewer needs no new probe beyond PRB-LIVE-06 and PRB-XE-06.
- Good, because the native viewer becomes the target, with the graph model built from day one.
- Bad, because the MVP's graph display depends on undocumented SSMS viewer APIs.

### An out-of-process viewer in the MVP
- Good, because it would not depend on SSMS's viewer APIs.
- Bad, because a new hand-off probe would have to join RES-NN-001 and pass before it counts at launch.
- Bad, because it is a second program to build, secure under NFR-048 and keep light, and the native viewer replaces it anyway.
