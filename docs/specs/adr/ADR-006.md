# ADR-006 — Build the tool windows in WPF with MVVM: view models in Core under the coverage gate, logic-free XAML views in a net48 project

## Context and problem statement

ARCH-001#DEC-06 asks what UI technology the tool windows use. Every MVP screen in DSN-001 is a tool window inside SSMS 22: the instance window and its tabs, the prompt builder and redaction preview, the settings, and the diagnostics window. The native viewers after the MVP (FR-056, FR-057) draw graphs in the same windows. The look must follow the Visual Studio 2026 shell's theme tokens (NFR-027, NFR-028), and NFR-044 puts the logic under a 95% line-coverage gate that CI measures on Linux.

## Decision drivers

- PRD-001#NFR-027 and NFR-028: the shell's look and theme tokens, in every theme.
- PRD-001#NFR-019: no lag on first paint or tab switch.
- PRD-001#NFR-044: logic under the 95% gate; only the thin VSIX is untestable.
- PRD-001#NFR-022 to NFR-026 and NFR-029 to NFR-030: status, table views, fonts, motion, keyboard and chart rules.

## Considered options

1. WPF, styled only with the shell's theme tokens.
2. A hosted web view (WebView2) rendering HTML.

## Decision outcome

**Chosen option:** option 1, WPF. Bryan Ankielewicz decided this on 2026-11-06. The decision text he pasted and confirmed notes that WPF creates code the Linux coverage gate can't run, so without a stated carve the first UI pull request either weakens the gate or stalls. It says:

> MVVM with the carve stated: view models and all logic live in Core (netstandard2.0, INotifyPropertyChanged is available) under the 95% gate; views are declarative XAML with no logic in code-behind, in a net48 project with no SSMS reference. The UI's evidence is PerfView against NFR-019. Theme only through the shell's token keys (INPUT-NN-018). No WebView2 and no charting dependency; charts and the native viewers draw with DrawingVisual on a virtualized canvas.

### Consequences

- Good: the coverage gate keeps its meaning. Every decision a screen makes is in a view model that Core's tests cover.
- Good: the views project has no SSMS reference, so it builds and loads without SSMS types (late binding stays in the host layer).
- Good: no WebView2 runtime and no charting library to load, which keeps SSMS light.
- Bad: charts and native viewers are drawn by hand with DrawingVisual, which is more work than a charting library.
- Bad: the views project is outside the coverage gate by design. Its evidence is PerfView against NFR-019 and a check in SSMS, never a lowered gate or a coverage exclusion.

### Confirmation

- The first UI epic adds the net48 views project with no SSMS reference and no code-behind logic beyond InitializeComponent (checked in review).
- Every view model is in Core, and CI's 95% gate covers it.
- PerfView traces on the local instance show first paint within 500 ms and no stall over 50 ms (NFR-019).
- Each window is checked in the Light, Dark and Cool Breeze themes (NFR-028).

## Pros and cons of the options

### WPF with the shell's theme tokens
- Good, because the shell's tokens are WPF resource keys, so the look follows SSMS's theme.
- Good, because nothing heavy has to start inside SSMS.
- Bad, because charts and graphs are drawn by hand.

### A hosted web view
- Good, because HTML and CSS make rich charts easy.
- Bad, because WebView2 is a heavy runtime inside SSMS and is slow to first paint.
- Bad, because the shell's theme tokens would have to be copied into CSS and kept in sync by hand.
