# ADR-007 — Keep per-user settings in a versioned JSON file under the user's local application data, written atomically

## Context and problem statement

ARCH-001#DEC-07 asks where per-user settings live: the redaction presets and object-name switch (FR-003, NFR-005) and the per-instance thresholds (NFR-043). The prompt builder, the redaction preview, the settings screen and every instance-window tab read them, and they are separate epics.

## Decision drivers

- PRD-001#NFR-005: settings are per user, with no administrator lock.
- PRD-001#NFR-008: no password or connection-string secret is stored.
- PRD-001#NFR-043: thresholds are edited per instance.
- PRD-001#NFR-044: the logic that reads and writes settings is unit-tested in Core.

## Considered options

1. A JSON file per user under `%LOCALAPPDATA%\NoName`, next to the logs.
2. The Visual Studio settings store inside SSMS.

## Decision outcome

**Chosen option:** option 1. Bryan Ankielewicz decided this on 2026-11-06. The decision text he pasted and confirmed asks this ADR to carry two additions: the schema version is in the file, the file is written atomically (to a temp file, then renamed), a corrupt file is backed up and reset with a notice, and if NFR-047 later brings SQL authentication the credentials go to Windows Credential Manager, never this file.

The same text raises a question that is new scope and the PRD owner's call: enterprise customers expect a machine-level policy file (in ProgramData, admin-writable) that overrides user settings for redaction rules, for example "always redact server names" or "paste-back off". This ADR doesn't decide it. It conflicts with NFR-005 and PRD-001's non-goal of an administrator-managed redaction policy, so it is recorded as an open question for the PRD owner in ARCH-001 section 8.

### Consequences

- Good: Core reads and writes the file with no SSMS types, so it is tested under the 95% gate.
- Good: an atomic write and a backed-up reset mean a crash or a bad edit never leaves the user without working settings.
- Good: the schema version lets a later release migrate the file.
- Bad: settings don't roam between machines. That fits NFR-005's per-user rule but isn't stated anywhere in the PRD.

### Confirmation

- The first epic that ships FR-003 specifies the file's schema, its version and the reset notice, and unit-tests the atomic write and corrupt-file reset in Core.
- No field of the file holds a password, token or connection-string secret (checked by a unit test and in review, NFR-008).

## Pros and cons of the options

### A JSON file under local application data
- Good, because Core can test it and a user can back it up or inspect it.
- Bad, because it needs its own atomic-write and corruption handling.

### The Visual Studio settings store
- Good, because SSMS manages it.
- Bad, because it needs SSMS types, so the logic can't be tested in Core.
- Bad, because SSMS 22 updates may change it.
