# ADR-005 — Feed every tab of an instance window from one shared sampler that measures its own cost

## Context and problem statement

ARCH-001#DEC-05 asks whether the tabs of an instance window share one sampler, or whether each tab polls the instance on its own. The KPI strip must be identical on every tab (FR-035), one time brush spans every tab (FR-048), polling is at 5 seconds or slower and stops while the window is hidden (FR-038), and the window shows the server cost of each poll (FR-013, NFR-020). The live monitor, Query Store, error-log, deadlock and health tabs are separate epics. Unless one sampler is decided, each epic would build its own poll.

## Decision drivers

- PRD-001#NFR-020: the server cost of each live poll stays under a target and is shown.
- PRD-001#FR-038: polling at 5 seconds or slower, paused while hidden, deltas rather than totals.
- PRD-001#NFR-018 and NFR-019: no SQL on the UI thread, first paint within 500 ms from cached data.
- PRD-001#NFR-031: every panel shows its sample age.

## Considered options

1. One sampler per instance window that feeds every tab, the KPI strip and the time brush.
2. Each tab polls the instance on its own.

## Decision outcome

**Chosen option:** option 1. Bryan Ankielewicz decided this on 2026-11-06 , with the cost mechanism NFR-020 needs, in the decision text he pasted and confirmed:

> One poll is one batch with multiple result sets. The sampler reads its own session's cpu_time, logical_reads and elapsed deltas from sys.dm_exec_sessions in the same batch; that is the per-poll cost the window shows. The KPI strip and time brush are the always-on base section; every other section runs only while a tab subscribes, so hidden tabs cost the server nothing. Ring buffers per counter in Core, tabs subscribe to the sampler, nothing else polls.

### Consequences

- Good: one batch per poll, so NFR-020's cost is one measured number, read from the sampler's own session.
- Good: hidden tabs cost the server nothing, and the KPI strip and brush stay identical on every tab because they come from the same samples.
- Good: the ring buffers give first paint cached data (NFR-019, NFR-031), and they live in Core under the 95% gate.
- Bad: the batch is shared, so a slow section delays every subscriber in that poll. The first epic that ships the sampler sets a per-section limit.
- Bad: NFR-020's target is still a NEEDS CLARIFICATION marker in PRD-001, so the mechanism exists before its limit does.

### Confirmation

- The first epic that ships FR-035 or FR-013 specifies the sampler, its base section, subscriptions and ring buffers, and unit-tests them in Core.
- No code outside the sampler opens a polling query on the extension's own connection (checked in review).
- ASM-25's prototype on the local instance shows the per-poll cost and no stall over 50 ms (NFR-019).

## Pros and cons of the options

### One shared sampler
- Good, because one cost is measured and shown, and hidden tabs cost nothing.
- Good, because the shared samples keep the KPI strip and time brush consistent.
- Bad, because one slow section delays the whole batch.

### Each tab polls on its own
- Good, because tabs are independent.
- Bad, because the server cost multiplies with each open tab, NFR-020 has no single number, and the KPI strip and brush can disagree between tabs.
