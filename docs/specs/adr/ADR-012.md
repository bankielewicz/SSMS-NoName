# ADR-012 — Feed every tab of an instance window from one shared sampler that measures each poll from its own running request

## Context and problem statement

ARCH-001#DEC-05 asks whether the tabs of an instance window share one sampler or each tab polls on its own, and how the per-poll server cost is measured. ADR-005 chose one shared sampler and measured the cost by reading the sampler's own session counters (cpu_time, logical_reads and elapsed deltas from sys.dm_exec_sessions) in the same batch. The Codex reviews of 2026-11-06 showed why that measurement is wrong. Session totals update only when a request completes, so a mid-batch read measures the previous poll, and session elapsed time includes the idle time between polls. This ADR supersedes ADR-005: it keeps the shared sampler and states the cost mechanism exactly as PRD-001 version 3's NFR-020 does.

## Decision drivers

- PRD-001#NFR-020: the server cost of each live poll stays under a target and is shown.
- PRD-001#FR-038: polling at 5 seconds or slower, paused while hidden, deltas rather than totals.
- PRD-001#NFR-018 and NFR-019: no SQL on the UI thread, first paint within 500 ms from cached data.
- PRD-001#NFR-031: every panel shows its sample age.

## Considered options

1. One sampler per instance window, with each poll measured from its own running request at the end of the batch.
2. ADR-005's measurement: the session's counters read mid-batch.
3. Each tab polls the instance on its own.

## Decision outcome

**Chosen option:** option 1. Bryan Ankielewicz decided this on 2026-11-06, answering the Codex reviews, and approved this supersession of ADR-005 in the same session.

**The sampler, unchanged from ADR-005.** One sampler per instance window. One poll is one batch with multiple result sets. The KPI strip and the time brush are the always-on base section, and every other section runs only while a tab subscribes, so hidden tabs cost the server nothing. Core keeps ring buffers per counter, tabs subscribe to the sampler, and nothing else polls.

**The cost, as PRD-001 version 3's NFR-020 states it.** The batch's last statement reads cpu_time, logical_reads, reads, writes and total_elapsed_time from sys.dm_exec_requests for @@SPID. These accumulate across the running request, so they cover the whole batch except that final cheap read, and the elapsed time is the request's, not the session's. The client's wall time around the batch comes from a stopwatch and is shown separately, because it includes the network. The sampler's queries run with OPTION (MAXDOP 1), for a lower server cost and no parallel-plan accounting oddities. The first poll's compile cost is shown, not smoothed. A reconnect starts a new request lineage, so there is nothing to subtract.

### Consequences

- Good: each poll's cost is that poll's own work, with no idle time and no carry-over from the previous poll.
- Good: one batch per poll, so NFR-020's cost is one measured number, and hidden tabs cost nothing.
- Bad: the final read of sys.dm_exec_requests isn't counted in its own figures (it is cheap).
- Bad: MAXDOP 1 can make a large section slower than a parallel plan would.
- Bad: NFR-020's target is still a NEEDS CLARIFICATION marker in PRD-001, so the mechanism exists before its limit does.

### Confirmation

- PRB-SQL-03's poll-cost step (RES-NN-001 0.2.4) runs a cheap and a deliberately expensive batch alternately and compares the reported logical_reads with SET STATISTICS IO captured through InfoMessage, within a stated tolerance, with the wall time logged separately.
- The first epic that ships FR-035 or FR-013 specifies the sampler, its base section, subscriptions and ring buffers, and unit-tests them in Core.
- No code outside the sampler opens a polling query on the extension's own connection (checked in review).

## Pros and cons of the options

### One shared sampler, measured from its own running request
- Good, because the measured cost is the poll's own.
- Bad, because one slow section delays the whole batch.

### ADR-005's mid-batch session counters
- Bad, because session counters read mid-batch measure the previous poll and include idle time: session totals update only when a request completes, and session elapsed time spans the polling interval.

### Each tab polls on its own
- Bad, because the server cost multiplies with each open tab, NFR-020 has no single number, and the KPI strip and brush can disagree between tabs.
